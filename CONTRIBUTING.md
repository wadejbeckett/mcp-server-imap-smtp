# Contributing

Contributions are welcome: bug reports, fixes, documentation and support for more mail server set-ups.

- **Before you start.** Open an issue first for anything larger than a small fix, so the approach can be agreed.
- **Set up.** `uv venv && uv pip install -e ".[dev]"`, then `.venv/bin/pytest`. Every change needs tests, and the suite must pass. Integration tests against a real mailbox are opt-in: `pytest -m integration`, with credentials from the environment (see docs/RUNNING.md).
- **Test lab.** `scripts/lab.sh up` starts three local mail servers in Docker (Dovecot 2.4 with Pigeonhole, and Postfix, from Debian's packages; the image is built from `lab/`), then `.venv/bin/pytest -m lab` runs the lab tests against them; `scripts/lab.sh down` removes the containers and their mail. Each profile listens on 127.0.0.1 only: `flat` (folders beside INBOX, every extension) on 10993 (IMAPS), 10143 (IMAP, STARTTLS required), 10465 (SMTPS), 10587 (submission, STARTTLS required) and 10190 (ManageSieve); `prefixed` (every folder under `INBOX.`) on 11xxx; `stripped` (flat, with MOVE, UIDPLUS and ESEARCH not advertised, for the fallback paths, and submission on 12587 without STARTTLS) on 12xxx. Dovecot still accepts those commands there, so a fallback test also asserts, with `record_commands` in `tests/_lab.py`, that the connector did not send them. The first `up` makes a private CA and a `localhost` certificate in `lab/.state/` (not committed); the tests trust only that CA. The fixture mailboxes `alice@example.test`, `bob@example.test` and `carol@example.org` and their lab-only passwords are in `lab/dovecot/users`; `sales@example.test` is a sending identity only alice may use (it receives no mail); the lab delivers only to its own domains and refuses to relay anywhere else. The servers have quota, ACL, METADATA, special-use folders and Sieve (vacation, fileinto, imap4flags, variables); submission enforces SIZE (25 MB), DSN, CHUNKING, SMTPUTF8 and that the envelope sender belongs to the signed-in mailbox. New tests that need a server should target the lab (helpers in `tests/_lab.py`) rather than a real mailbox. `tests/test_lab_e2e.py` starts the real connector as a process against each lab profile (`running_connector` in `tests/_lab.py`, reusable for other end-to-end cases) and runs `deploy/e2e.py` against it with `--write --send`; a change that breaks the OAuth flow, the sign-in page or a tool an AI app relies on fails there.
- **Continuous integration.** GitHub Actions runs on every pull request and every push to `main`: the unit suite on Python 3.11 to 3.14 with dependencies from `uv.lock` (`uv sync --locked`, so a stale lock fails), the lab tests once, and shellcheck, a compile of `deploy/e2e.py` and a wheel and sdist build for the deploy kit; integration tests never run there. A pull request must be green on every check before it is merged.
- **Clean-machine install test.** `scripts/install-test.sh` checks that a stranger can install the gateway from the docs: it boots the official Debian 13 cloud image (downloaded over HTTPS and checked against Debian's SHA512SUMS, then cached) in a throwaway QEMU VM, starts one lab mail server container for it to sit in front of, clones the checkout, builds the bundle with `deploy/build.sh`, installs it with the command in docs/DEPLOY.md and a certificate from a test CA (`TLS_CERT`), binds it to the mail server, and runs `deploy/smoke.sh` and `deploy/e2e.py --write --send` against it from the host. `--upgrade <git revision>` installs that revision first, keeps a signed-in connection, installs HEAD over it and checks that the connection still works. It exits non-zero on any failure and removes the VM and the container at the end (`KEEP=1` leaves them for a look; `scripts/install-test.sh down` removes them). It needs `qemu-system-x86_64` with a usable `/dev/kvm`, `qemu-img`, `genisoimage`, docker, `ssh`, `openssl`, `git`, `python3` 3.11 or later and `uv`, about 3 GB of disk and no root; it takes about 4 minutes (6 with `--upgrade`) once the image is cached, plus the first download of the image (about 430 MB). After a failed run the VM's console log and the build and install logs are kept in `last-failure/` under `INSTALL_TEST_DIR`. It cannot test a public name, real DNS or Let's Encrypt issuance, or Debian 12; the header of the script says what else it stands in for.
- **Style.** Keep the style of the surrounding code: small functions, plain names, and comments that explain why rather than what.
- **Security.** The connector holds other people's mail passwords. Changes to sign-in, sealing, tokens or the mail server binding get extra review. Never log message content, recipients, tokens or passwords.
- **No company specifics in the code.** Operator names, hosts and limits belong in the configuration.
